# Repository Architecture Standard

## Status
Canonical operating standard

## Promoted
September 29, 2026 from the parallel FC-002 architecture package and reconciled under the ratified constitutional layer.

---

# Purpose

This standard defines how Finding My Wei repositories and major repository layers are implemented.

The Constitution defines authority and institutional identity.

This document governs implementation beneath that authority.

---

# Governing principle

> **Integration over Reorganization.**

Existing structures should be preserved when they are coherent, useful, and validated by real work.

Reorganization is justified when it resolves conflicting authority, duplicate canonical sources, broken navigation, stale operating machinery, or material stewardship friction.

Uniformity by itself is not sufficient reason to restructure.

---

# Inventory before intervention

Before creating, moving, renaming, consolidating, archiving, or deleting substantial repository content:

1. inspect the actual repository state;
2. identify active workstreams and dependencies;
3. identify canonical documents and competing authority;
4. preserve unique knowledge and provenance;
5. protect active production;
6. define the intended canonical destination;
7. then execute the smallest useful structural change.

---

# Canonical-source rule

Every enduring document should have one canonical home.

Cross-reference rather than maintain uncontrolled duplicates.

When an operational copy is necessary, identify its canonical source.

A historical artifact may remain preserved without remaining authoritative.

---

# Functional placement

Content should live with the function or enduring body of knowledge it serves.

Typical functions include:

- constitutional authority;
- operating standards;
- current operating state;
- domains / enduring knowledge;
- bounded projects and campaigns;
- publishing and distribution;
- assets;
- research/reference;
- archive/provenance.

These are functions, not a requirement to create empty folders.

---

# Navigation

Major repository surfaces should be understandable without undocumented Founder knowledge.

README, START_HERE, maps, and charters are navigation aids. They do not replace the canonical authority of the documents they point to.

Do not create navigation layers that become competing truth systems.

---

# Naming

Preserve coherent established naming where possible.

For new institutional Markdown documents, `UPPER_SNAKE_CASE.md` is preferred when consistent with the surrounding canonical layer.

Do not rename merely for cosmetic consistency when the change adds migration risk without reducing ambiguity.

Case variants that create competing canonical roots are not cosmetic and should be reconciled.

---

# Active production protection

Repository cleanup must not destabilize a working production system merely to satisfy an abstract architecture diagram.

Proven operational systems receive special protection until dependencies, references, and replacement paths are understood.

---

# Archive rule

Archive preserves provenance; it does not compete for current authority.

Git history may provide sufficient exact preservation when copying full legacy trees would create new duplication.

Archive manifests should explain disposition and canonical successors where needed.

---

# Stewardship test

A structural change is successful when it reduces the amount a future steward must infer.

The goal is not the fewest folders or the most elegant diagram.

The goal is **clear authority, reliable navigation, preserved knowledge, and low operational friction**.
