# Purpose

This document recognizes the production system proven through real-world use, particularly Tao Issues 013 and 014.

The Constitution governs what must remain true. This playbook governs how approved publication work moves safely from idea to deployed production.

Detailed issue receipts remain the evidence record. This playbook defines the reusable pattern.

---

# Core Rule

**Governance protects intent. Production moves approved work.**

The production system should be rigorous enough to prevent unauthorized or incomplete deployment, but no more complicated than required to achieve that result.

---

# Canonical Production Flow

## Stage A — Editorial Development

1. Establish the issue or campaign objective.
2. Develop editorial direction.
3. Identify source material and approved language.
4. Do not begin downstream production before editorial direction is ready for Founder review.

**Gate:** Founder approval of editorial direction.

## Stage B — Asset Production and Completeness

1. Build required visual and written assets.
2. Register the canonical asset set.
3. Confirm expected object counts and destinations.
4. Resolve missing, duplicate, orphaned, or ambiguous assets before deployment.

**Gate:** Production completeness confirmed.

## Stage C — WordPress / Primary Publication

1. Assemble the canonical long-form article from approved material.
2. Confirm title, slug, permalink, featured image, metadata, and publication time.
3. Where automated authentication is unavailable, use a bounded Founder Manual Bridge rather than guessing or bypassing controls.
4. Verify the publication state to the maximum technically available extent.

**Gate:** Primary publication is scheduled or otherwise confirmed and its dependencies are understood.

## Stage D — Distribution

### Buffer / Social

1. Create only the approved objects.
2. Use canonical assets and approved copy.
3. Read back scheduled objects when technically possible.
4. Reconcile destination, timestamp, copy, media, and status.

### Brevo / Email

1. Use the approved sender identity and audience boundary.
2. Confirm subject, preheader, body, CTA, recipient list, and schedule.
3. Preserve permission boundaries between brands and audiences.
4. Read back the live campaign object before execution when possible.

**Gate:** All distribution objects reconcile against the approved production package.

## Stage E — Final Reconciliation and Receipt

1. Count every publication object.
2. Confirm each expected object exists exactly once.
3. Record unresolved technical limitations explicitly rather than implying certainty.
4. Produce an execution or deployment receipt.
5. Close the issue only after the complete system reconciles.

**Gate:** PASS / HOLD / FAIL recorded with evidence.

---

# Founder Gates

Founder approval is required where a decision changes:

- Intellectual intent or meaning
- Final editorial direction
- Unapproved connective or original copy presented as Founder-authored
- Audience or sending identity
- Public publication or irreversible deployment when not already authorized
- Material deviation from the approved production package

Founder attention should not be consumed by mechanical verification that can be performed reliably by the operating system.

---

# Evidence Doctrine

Production claims must distinguish among:

- **Machine verified** — independently retrieved or reconciled.
- **Founder confirmed** — verified directly by Drew where system access prevents independent retrieval.
- **Inferred** — supported by evidence but not directly verified.
- **Unknown** — not established.

Never silently convert Founder confirmation or inference into machine verification.

---

# Exception Rule

When a production system blocks automation:

1. Stop at the boundary.
2. Define the smallest manual action required.
3. Give the Founder exact instructions.
4. Resume automated verification after the manual bridge.

Do not create workarounds that weaken permission, provenance, security, or evidence quality.

---

# Reuse Rule

A proven production pattern should be inherited unless new evidence shows that it is unsafe, inaccurate, obsolete, or inappropriate for the new issue.

Do not redesign the pipeline for every publication cycle.

---

# Relationship to the IEMS

This playbook is subordinate to the Constitution and belongs in the Operating System because it describes how work moves through production.

Issue-specific editorial briefs, asset registries, schedules, deployment receipts, and execution receipts remain with their campaigns as evidence.

The playbook is the reusable operating doctrine; the receipts are the historical record.
